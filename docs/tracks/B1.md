# B1: frozen boris artifact

Status: done. `boris-site/` is a 12-page site with committed artifacts,
`stage-check.sh` is the reference behavior for `knap_publish_check`, and
`ask.sh` is the reference query for `boris_ask` / `boris_check`.

All numbers below were measured on Oct 26 with `boris/0.8.2`
(`~/.local/bin/boris`), Apple M4 (10 cores), macOS 27.2. Other agents were
building on the same machine, so tails are noisy; medians are stable across
passes.

## 1. The check command

```sh
cd <site-copy>   # boris resolves output paths against the working directory
boris check --input content --format json --report report.json --quiet
```

**There is no flag for unresolved links, and none is needed.** A wiki-link
to a missing page is a hard graph error (`EREFERENCEMISSING`) in every boris
mode: `check`, `validate`, HTML build, IR, RAG. SPEC's
`boris check --fail-on-unlinked` does not match the binary:

- 0.8.2 rejects `--fail-on-unlinked` as a usage error (exit 2).
- boris `main` (v0.9.0+, #1023) has it, but it fails on `unlinked_page`: a
  page with *no edges at all*. That is not reference resolution.
- `--fail-on-unreferenced` exists in 0.8.2 but fails whenever any page lacks
  an inbound link. A staged doc is always unreferenced, so it always fails.
  Do not use it.

Exit codes (`check` and `validate`):

| Exit | Meaning |
|---|---|
| 0 | Graph valid. Findings such as `unreferenced_page` are informational |
| 1 | Content or graph invalid: `EREFERENCEMISSING`, `EREFERENCESYNTAX`, `EFRONTMATTER`, ... |
| 2 | Usage (unknown flag, output path outside the working directory: `WorkspaceEscape`) |
| 3 | I/O (for example a missing content root, `EIO`) |

Output:

- Success: the analysis report (human, or JSON with `--format json`) goes to
  stderr, or to `--report PATH`. Stdout is always empty. The JSON is
  `{"format": "boris-documentation-intelligence", "schemaVersion": "0.2.0", ...}`
  with `summary.pages`, `nodes`, `edges`, `findings`.
- Failure: no JSON is written, even with `--format json --report`. Stderr has
  one line per diagnostic, every missing reference reported (not just the
  first):

  ```text
  error: EREFERENCEMISSING: staged/verdict.md:44:3: wiki-link target "acmedb-soc-2-audit-report" not found in the page graph [Point the wiki-link at an existing page entity id, and if using #heading-id match a rendered heading id on that page]
  ```

  Shape: `error: CODE: path:line:col: message [remediation]`. `path` is
  content-relative. `line` is the 1-based **file** line (frontmatter lines
  count; the boris contract text says body-relative, the binary disagrees).
  `col` is a 1-based **byte** column (`- é — [[x]]` reports col 10).

What `check` does not catch: `[[page#missing-heading]]`. It validates graph
targets only. `boris validate` renders in memory and catches heading
fragments too (only after every entity target resolves).

### The JSON alternative: `boris validate`

```sh
boris validate --input content --report report.json --quiet
```

Writes nothing except the report, which it writes on success **and** failure:

```json
{"schemaVersion": "html-build-report-0.2.0", "compilerId": "boris/0.8.2", "vcsRevision": "897611b7",
 "ok": false, "contentRoot": "content", "outDir": "dist", "errorCount": 1,
 "diagnostics": [{"severity": "error", "code": "EREFERENCEMISSING",
   "message": "wiki-link target \"acmedb-soc-2-audit-report\" not found in the page graph",
   "remediation": "...", "sourcePath": "staged/verdict.md", "line": 44, "column": 3,
   "id": "acmedb-soc-2-audit-report"}]}
```

It needs the layout at `themes/boris/layouts/main.html` (copied with the
site). Cost: about 1.5 to 2 ms more than `check`. **Recommendation for B2:** use
`validate --report` and parse JSON; fall back to parsing `check` stderr only
if the extra milliseconds matter.

## 2. Staging without touching the frozen site

Boris has no overlay or multi-root input, so staging is copy-to-temp:

1. `mktemp -d`, copy `content/` and `themes/` into it (14 small files).
2. Adapt the doc and write it to `content/staged/<name>.md` (id
   `staged/<name>`; `<name>` is the doc's basename with bytes outside
   `[A-Za-z0-9._-]` replaced by `-`).
3. `cd` into the temp dir and run the check there (`--out`/`--html-dir` must
   be under the working directory; `--report` may point anywhere).
4. Map diagnostics back, delete the temp dir.

`check` and `validate` write nothing besides `--report`; verified by listing
files newer than the staged doc after a run.

### The adapter (B2 must port this)

A knap-rendered doc does not parse as a boris page as-is. Both mismatches
were hit with the shipped `verdict` sample:

| knap output | boris says | Adapter rule |
|---|---|---|
| Frontmatter from `{{ frontmatter \| yaml }}`: `year:`, `genre:` + YAML list, `verdict:` | `EFRONTMATTER: unsupported frontmatter key` (closed key set, no YAML lists) | Replace the block with `title` only (double-quoted unless the title contains `"`) |
| `{{ s.name \| wikilink }}` → `[[AcmeDB docs — backups]]` | `EREFERENCESYNTAX: malformed wiki-link` (ids cannot contain whitespace) | `[[T]]` → `[[slug(T)\|T]]`; `[[T\|L]]` → `[[slug(T)\|L]]`; `#frag` kept; slug-form targets untouched |

`slug`: ASCII lowercase; keep `[a-z0-9/]`; every other run of bytes
(spaces, punctuation, UTF-8 like `—`) becomes one `-`; trim `-` and `/` from
both ends. An empty slug leaves the link alone, so boris reports the syntax
error.

Body lines are never added or removed, so mapping back is exact:
`stage-check.sh` records each link's staged and original (line, col) and
shifts any other body diagnostic by the frontmatter size difference.
`![[embed]]` resolves the same way (boris reports the column of the `[[`).

Trade-off: the slug folds case and punctuation, so a near-miss name that
slugs to a real id ("AcmeDB Docs: Backups") passes. A wrong source name
fails. Exact ids remove the fold; see "For other lanes".

## 3. Latency

`./bench.sh verdict.md verdict.hallucinated.md 50` (50 runs per case,
fork+exec timed with Time::HiRes, so process spawn is included):

| Case | median ms | min | p90 | max |
|---|---:|---:|---:|---:|
| process floor: `boris --version` | 2.4 | 2.1 | 3.0 | 3.5 |
| `check`, frozen site, warm | 3.4 | 2.8 | 4.3 | 6.0 |
| `check`, staged verdict, warm | 3.2 | 2.8 | 3.7 | 5.2 |
| `check`, staged verdict, cold | 4.0 | 3.3 | 4.9 | 6.5 |
| `validate`, staged verdict, warm | 5.1 | 4.4 | 6.1 | 7.6 |
| `validate`, staged verdict, cold | 5.4 | 4.7 | 6.6 | 9.1 |
| `stage-check.sh` clean, end to end | 52.5* | 38.6 | 103.9* | 226.4* |
| `stage-check.sh` hallucinated, end to end | 46.7 | 43.7 | 50.7 | 68.6 |
| `stage-check.sh --validate` clean | 40.3 | 38.9 | 41.9 | 49.3 |

\* A burst of load from parallel agent builds hit that series. An earlier
50-run pass gave median 40.8, p90 44.7, max 53.6 for the same case.

- **Warm** = repeated runs in the same directory. **Cold** = each run in a
  freshly copied directory that boris has never read (setup untimed). The OS
  page cache was not purged (`purge` needs root), so "cold" is not a
  cold-disk number. For the boris rows, the first sample of a series ran
  at most about 3 ms above its median across passes.
- The site is 13 pages with the staged doc. These numbers say nothing about
  large sites.
- `stage-check.sh` overhead is shell plumbing, not boris: gawk startup is
  about 10 ms per call (two calls), `mktemp` + `cp -R` + `rm -rf` about
  15 ms. With BWK `/usr/bin/awk` first on `PATH` the end-to-end median drops
  to 34 ms. A Zig port that copies in-process and spawns boris once should
  land near the `check, cold` row plus the copy.

**Claim this:** `boris check` on the staged doc takes about 4 ms median
(cold) and `boris validate` about 5 ms, spawn included, on this site and
machine. Layer 3 is sub-100 ms with wide margin; even the shell reference
has a median of 40 to 53 ms.

## 4. Artifacts and how to query them

`./build.sh` regenerates all of these from `content/`; `./build.sh --check`
rebuilds into a scratch dir and diffs. No timestamps or absolute paths;
`completion.json` and the RAG manifest name the compiler version.

| File | Producer | Format | Use |
|---|---|---|---|
| `artifact/search-index.json` | HTML build (`dist/_boris/search/`) | `boris-rendered-search-index` v1 | Ranked snippets |
| `artifact/completion.json` | IR build (`--out`) | `boris-completion-index` v1 | Per-page tags + relations |
| `artifact/graph.json` | IR build | IR `0.3.0`, `frozen: true` | Full graph: edges, reverse index, nav |
| `artifact/rag/working-1.md` | `--rag-dir` | `boris-rag` schema 2 working pack | Whole-site context for a model |
| `artifact/rag/manifest.json` | `--rag-dir` | RAG sidecar, per-doc sha256 | Integrity |

"source-rag" in SPEC: in boris, `boris-source-rag` is a separate tool that
packs a *code repository*. The product RAG export is `boris --rag`. We use
the latter.

### search-index.json (boris_ask)

```json
{"format": "boris-rendered-search-index", "schema_version": 1, "documents": [
  {"path": "acmedb-docs-backups.html", "title": "AcmeDB docs — backups", "sections": [
    {"level": 2, "heading": "What it says", "fragment": "what-it-says",
     "text": "Point-in-time snapshots are coming soon. Cross-region replication is on the roadmap. ...",
     "code": ""}]}]}
```

- One document per page, sorted by `path`; entity id = `path` minus `.html`.
- Sections in document order. `level` 0 is text before the first heading;
  `fragment` is the rendered heading id (link target `path#fragment`).
- `text` is prose with code removed; inline code goes to `code`. Keep
  inline code out of prose you want to snippet.
- Consumers must reject a wrong `format` or `schema_version`.

Ranking (`ask.sh`, a port of the boris starter theme's browser search
client): lowercase the query, split on whitespace; per section, for each
term add 12 if the page title contains it, 8 for the heading, 2 for text, 1
for code; add 1 for a level-1 section and 5 if the whole query appears. A
page scores its best section; ties sort by path, then section order. One
change from the theme: a section needs at least one term hit (the theme
lets the level-1 bonus alone match every page). The theme also applies
NFKD and strips diacritics; `ask.sh` does ASCII lowercasing only.

```sh
$ ./ask.sh -k 1 "point-in-time snapshots"
{"score":9,"id":"acmedb-docs-backups","path":"acmedb-docs-backups.html","fragment":"what-it-says","title":"AcmeDB docs — backups","heading":"What it says","snippet":"Point-in-time snapshots are coming soon. Cross-region replication is on the roadmap. The page documents one operation: a manual dump to a local file. …"}
```

### completion.json (boris_check)

```json
{"format": "boris-completion-index", "schema_version": 1,
 "compiler_id": "boris/0.8.2+semantic-relations", "frozen": true, "entities": [
  {"id": "claims/backup-gap", "title": "AcmeDB has no managed backups", "parent": "claims",
   "role": "satellite", "status": null, "tags": ["claim", "supported"],
   "relations": [{"kind": "cites", "target": "acmedb-docs-backups"}]}]}
```

Claim pages carry exactly one verdict tag (`supported`, `refuted`,
`unverified`) and `cites` relations (custom relation kinds are legal:
`[a-z][a-z0-9_]{0,63}`). Source URLs are in the source page's level-1
section text (`URL: https://...`).

`./ask.sh --claims "AcmeDB backups"` ranks claim pages only and attaches
`verdict` and `cites`. That is retrieval, not a yes/no decision. For B3:

- Map the verdict tag, not the query: `supported` → yes, `refuted` → no,
  `unverified` → unknown, for **the recorded claim**. "Does AcmeDB have
  managed backups?" retrieves "AcmeDB has no managed backups" (supported);
  the honest answer is "the artifact supports the opposite", not "yes".
  Return the matched claim text with the answer so the polarity is visible.
- Every claim title contains "AcmeDB", so a term shared by all claims always
  matches. Require coverage (for example, at least half the query's
  non-stopword terms found in the matched page) or answer unknown.
  "AcmeDB supports SQL" must not return the top claim's verdict.

```text
  [[AcmeDB SOC 2 audit report]] -> acmedb-soc-2-audit-report

  [[AcmeDB SOC 2 audit report]] -> acmedb-soc-2-audit-report

```

`selftest.sh` renders both samples with `knap-mcp render <id> --target
markdown --out`, inserts one invented source line into the verdict, and
expects exit 0, 0, 1 (check) and 0, 1 (validate). Both
`/usr/bin/awk` (BWK) and GNU awk produce the same output.
