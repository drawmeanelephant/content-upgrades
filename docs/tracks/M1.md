# M1: live backends

Lane notes for the `backend.zig` work (#89 and friends).

## ACP backend feasibility — research for #127

Question: can `backend.complete` drive a local ACP agent (subscription plan,
no MODEL_API_KEY) as another `--backend` choice, and is it worth it for the
#90/#91 evals while #85/#86 are pending?

### What `backend.zig` actually requires

- `Kind` is a closed enum `{mock, spark, wonder, baseten}`; `parseKind` maps
  CLI/env strings. Adding `.acp` is one enum member — every `--backend` flag
  and `KNAP_BACKEND` picks it up automatically.
- `complete(ctx, kind, task, system, user) Error![]const u8` returns the
  reply text and nothing else. No usage struct, no latency field — callers
  measure their own ms and count their own calls (`ratchet.zig`
  `Result.calls`, `eval.zig` rows). An ACP backend only has to produce one
  `[]const u8` per call.
- Output discipline is per-caller, not per-transport: repair strips fences
  and rejects echo/prose (`sanitizePatch`), verifier strictly parses
  `{"label","score"}` (`parseDecision`), ratchet `parseReply`, voice
  `cleanReply` + guard. Whatever ACP returns goes through the same
  scrubbers unchanged.
- Errors: `ctx.fail` → `error.ToolFailed` + `ctx.err_msg`; every caller
  degrades (repair → non-convergence step, verifier → heuristic fallback,
  voice/ratchet → rejected). ACP failure modes slot straight in.
- `knap-mcp backends` (`cmdBackends` in `main.zig`) lists the enum; live
  rows are keyed on `MODEL_API_KEY` presence only — no probe. An `acp` row
  would key on `KNAP_ACP_AGENT` being set and resolvable.
- `mock` stays canned-only by design: `complete(.mock)` errors, and each
  feature keeps its own canned path (`mockPatch`, voice `.jsonl`, ratchet
  mock table). ACP does not change that.

### ACP client shape (subprocess stdio, newline-delimited JSON-RPC)

ACP is agent↔client, not model↔server: spawn the agent as a subprocess,
talk JSON-RPC 2.0 over stdio — the same framing `mcp.zig` already runs
inbound, and the same spawn/pipes/deadline pattern `runCurl` uses.

Minimal surface: `initialize`, `session/new`, `session/prompt`,
`session/cancel`, plus collecting `session/update` notifications
(`agent_message_chunk` content) for the reply text and reading the
`session/prompt` result's `stopReason`. ~4 methods + 1 notification.

- **Lifecycle:** one agent subprocess per knap-mcp process, spawned lazily
  on the first `.acp` call; one `session/new` per `complete` call so repair
  iterations and voice slots stay isolated (each iteration's slice is a
  fresh prompt; carried-over history is noise). Reusing one session is the
  cheaper alternative but lets turns bleed into each other.
- **Spawn-per-call is off the table** — agent init is seconds, and the
  evals make O(10²) `complete` calls.
- **Prompt mapping:** ACP prompt content blocks have no system role.
  Concatenate `system + "\n\n" + user` into one text block (or two ordered
  text blocks).
- **Reply:** collect `agent_message_chunk` text only; ignore
  `agent_thought_chunk` and `tool_call` updates. Advertise no fs/terminal
  client capabilities and deny `session/request_permission` — the contract
  is prompt-in/text-out.
- **No temperature control, no metering.** Reproducibility is weaker than
  `temperature: 0` over HTTP, and there are no tokens for the numbers card.

### Agents available on this machine

- `devin acp` — stdio ACP server. `--agent-type summarizer` is explicitly a
  no-tools, full-text-out agent; `--model` accepts fuzzy names. Best fit.
- `gemini --acp` — stable ACP flag (`--experimental-acp` deprecated). Runs
  its full agent loop with tools, so it leans harder on capability refusal.
- `codex` — no built-in `acp` subcommand (only experimental `app-server`);
  the `codex-acp` adapter exists upstream but is not installed.
- Config surface: `KNAP_ACP_AGENT` = argv string, e.g.
  `devin acp --agent-type summarizer`.

### Cost/latency vs the HTTP path

- Marginal cost is subscription/included rather than metered per token —
  that is the point of the exercise.
- Latency is materially worse: an HTTP chat call is ~1–2 s; an ACP turn is
  agent-loop startup plus model RTT, realistically 3–15 s+ even for a
  no-tools agent. Tolerable for eval tables (repair ≤4 calls/seed, ratchet
  capped at 10 calls/row), annoying interactively.

### Verdict: yes, with scope limits

Build it as a **fallback live path**, not a substitute for #89.

- It unblocks a real (non-canned) model through `complete` today and stress
  tests `sanitizePatch`/`parseDecision`/`parseReply` against agent-shaped
  output while `MODEL_API_KEY` is pending (#85, deadline Nov 4). If the
  credits slip, it is the only live-model path that exists.
- It does **not** deliver #90/#91 as written: those tables must cite
  spark/wonder/baseten numbers for the sponsor story. An `acp` row is a
  separate column — it derisks the plumbing, not the storyboard numbers.
- Work estimate: ~400–600 LOC of Zig (`acp.zig` client reusing `mcp.zig`
  framing + the `runCurl` spawn pattern), the `Kind.acp` member, a
  `backends` row, `KNAP_ACP_AGENT` parsing. One lane PR, medium effort.
  Smoke target: `devin acp --agent-type summarizer` on one eval seed.
- Risks: agents reaching for tools (mitigate with the no-tools agent type
  and capability refusal), output discipline (existing sanitizers), no
  `temperature: 0` (record in eval provenance).

This refines `docs/acp-backend.md` ("later goal, not on the critical
path"): the design stands, and #85's pending state is the argument for
pulling it forward — as plumbing insurance, not as the numbers source.

## Live smoke and offline robustness (#89)

> **PENDING MODEL_API_KEY** (#85). The offline half of #89 has landed:
> configurable endpoints, defensive reply parsing, `usage` capture, and a
> temperature setting with a guard. The smoke table below stays empty until
> a key exists. Nothing here was measured against a live provider.
>
> The ACP note above says `complete` returns no usage struct. It still
> doesn't, but `completeReply` (below) now does.

### What landed offline (`knap-mcp/src/backend.zig`)

- **Endpoint config, no code change needed.** Each setting reads
  `KNAP_<KIND>_*` before falling back to the built-in default. `<KIND>` is
  `SPARK`, `WONDER` or `BASETEN`:

  | var | default |
  |---|---|
  | `KNAP_SPARK_URL` / `KNAP_WONDER_URL` | `https://api.meta.ai/v1/chat/completions` |
  | `KNAP_BASETEN_URL` | `https://api.baseten.co/v1/chat/completions` |
  | `KNAP_SPARK_MODEL` | `muse-spark-1.3` (unconfirmed) |
  | `KNAP_WONDER_MODEL` | `muse-wonder-1.0` (unconfirmed) |
  | `KNAP_BASETEN_MODEL` | `meta-models/muse-spark-open-1026` (unconfirmed) |
  | `KNAP_<KIND>_MODELS_URL` | URL with `/chat/completions` → `/models` |
  | `KNAP_<KIND>_TEMPERATURE`, then `KNAP_TEMPERATURE` | `0`; `omit` drops the field; anything else must be a number in [0, 2] |

- **Temperature guard.** If the provider answers 400 or 422 and the body
  mentions `temperature`, the request is retried once without the field,
  with a note on stderr.
- **`backend.listModels(ctx, kind)`** sends `GET /v1/models` and returns
  the ids. It accepts OpenAI `{"data":[{"id"}]}`, `{"models":[…]}`, a bare
  array, string items, and `name` in place of `id`. No CLI row calls it
  yet (main.zig is outside this lane).
- **`backend.completeReply`** returns a `Reply` with `content`,
  `reasoning`, `finish_reason` and `usage`. `complete` still returns only
  the content, so its callers don't change.
- **Reply shapes accepted.** `message.content` can be a string, null, or an
  array of parts (`text` / `output_text`, `{value}`-wrapped text, and
  `reasoning` / `thinking` parts). Reasoning can also arrive in
  `reasoning_content` / `reasoning`, or as a leading `<think>…</think>`
  block. Legacy `choices[0].text` works, and so does an `error` object
  returned with HTTP 200. Reasoning is always split out of `content`, so
  JSON-only callers (ratchet enrich) see only the answer.
- **Degrade semantics (#45/#50).** Structural breakage is a `ToolFailed`.
  Empty or reasoning-only answers come back as `""`, which callers already
  treat as "no proposal". A repair reply with `finish_reason: length` is
  dropped (null patch), because a truncated region can still validate
  with template lines missing.
- **`usage`.** The parser reads `prompt_tokens`, `completion_tokens` and
  `total_tokens` (or `input_tokens` / `output_tokens`) plus
  `*_tokens_details.reasoning_tokens`. Fields the provider leaves out stay
  null and are never estimated. `KNAP_DEBUG=1` prints them per call on
  stderr.
- **Fixtures.** Every reply fixture in the backend.zig tests is invented,
  modeled on a public OpenAI-compatible shape, and labeled with what it
  assumes. Swap in real captures from the smoke.
