# CLI218: surplus-positional follow-up (issue #218)

Lane CLI218. Owner file: `knap-mcp/src/main.zig` (+ this note).

## Finding: the spec's premise was stale

#218 assumed `ratchet-eval`, `publish-check`, `density`, and
`structhash` still drop surplus positionals (from the AC lane's
unverified leftover note). Verified against the built binary at HEAD —
every `.custom` handler already rejects or uses them:

- `ratchet-eval foo` → `unknown option 'foo'` + usage, exit 1
  (`ratchet.zig` `cmdEval` else-branch, there since #27).
- `publish-check foo extra` → `needs exactly one doc_id` + usage,
  exit 1 (`args.len != 1` guard, there since #25).
- `density foo extra` → `needs exactly one doc_id or file` + usage,
  exit 1 (same guard, #27).
- `structhash a b` → variadic by design (sha256sum-style): each
  positional is hashed, none dropped. `structhash good bad` fails on
  `bad`, so positionals past the first are read.

`eval`, `serve`, `backends`, `ask`, `smoke` already reject stray args
too; `-h`/`--help`/`-v`/`--version` intentionally discard them.

## What landed

No behavior change — there was nothing left to fix. Two regression
tests in `main.zig` lock the contract in:

- `custom commands reject surplus arguments` — drives every `.custom`
  row in `commands` (minus the `-h`/`--help`/`-v`/`--version` meta
  rows) with two bogus positionals and asserts a nonzero exit, so a
  future handler can't silently drop them.
- `structhash positionals are all hashed, not dropped` — two real
  files hash fine (exit 0), and a bad second name fails (exit 1),
  pinning down that the variadic tail is consumed.
